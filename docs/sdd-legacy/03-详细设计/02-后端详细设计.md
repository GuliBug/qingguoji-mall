## 1. 分层规则

```
mall/controller  →  mall/service  →  mall/repository  →  DB
       ↓                ↓
   common / framework（单向依赖，反向禁止）
```

**硬性约束**（评审时逐条检查）：

| 约束 | 原因 |
|---|---|
| Controller 不写业务逻辑，只做参数接收与结果包装 | 保证业务可被测试直接调用 |
| Controller 不直接注入 Repository | 避免绕过服务层的事务边界 |
| Service 之间可互相调用，但不得循环依赖 | 循环依赖在 Spring 启动时才暴露，代价高 |
| `common` / `framework` 不 import `mall.*` | 保证这两层可整体复制到其他项目 |
| 实体不直接作为客户端入参，统一走 `dto` | 防止前端改 `member.points` 这类越权字段 |
| 返回给前端的分页在 `common` 层统一包装 | 避免各 Controller 各写一套 |

## 3. 通用层实现

### 3.1 AjaxResult

```java
public class AjaxResult<T> {
    private int code;
    private String msg;
    private T data;

    public static <T> AjaxResult<T> success()                  // code=200, msg="操作成功"
    public static <T> AjaxResult<T> success(T data)            // 同上，带数据
    public static <T> AjaxResult<T> success(String msg, T data)
    public static <T> AjaxResult<T> error(String msg)          // code=400
    public static <T> AjaxResult<T> error(int code, String msg)
    public static <T> AjaxResult<T> unauthorized(String msg)   // code=401
}
```

**设计要点**：`data` 为泛型，`null` 时 Jackson 输出 `"data": null`（不省略字段），前端可稳定按 `res.data` 取值。

### 3.2 BaseController

```java
protected <T> AjaxResult<TableDataInfo<T>> getDataTable(Page<T> page) {
    return AjaxResult.success(TableDataInfo.of(page));
}

protected PageRequest buildPageRequest(int page, int size, String sortProperty, Sort.Direction dir) {
    // page 从 0 开始；size 兜底 10；sort 默认 createdAt
}

protected Long getMemberId() { return LoginHelper.getMemberId(); }
```

**为什么把分页构造放在基类**：三个 Controller 有完全相同的一行 `PageRequest.of(...)`，抽出来后各 Controller 只保留业务调用，也统一了默认排序字段。

### 3.3 全局异常

```java
@ExceptionHandler(ServiceException.class)      // → code 400，msg 原样，日志 warn
@ExceptionHandler(MethodArgumentNotValidException.class)  // → code 400，取首个字段错误
@ExceptionHandler(Exception.class)             // → code 500，"系统繁忙，请稍后重试"，日志 error + 堆栈
```

**注意**：`ServiceException` 的文案会直接展示给用户，所以所有 `throw new ServiceException("...")` 都必须是可读中文，不能拼接英文技术术语。

## 4. 鉴权实现

### 4.1 令牌模型

```java
// TokenService
Map<String, Long>   memberTokens   // "MBR-xxx" → memberId
Map<String, String> adminTokens    // "ADM-xxx" → username
```

| 方法 | 说明 |
|---|---|
| `createToken(memberId)` | `MBR-` + UUID 去横线，写入 map |
| `getMemberId(token)` | 查 map，无则 null |
| `adminLogin(username, password)` | 与 `Constants` 中的固定账号比对，成功签发 `ADM-` |
| `getAdminName(token)` / `isAdmin(token)` | 校验管理端令牌 |

**为什么用两张表而不是一张带 type 的表**：会员 ID 是 `Long`、管理员是 `String`，分开存类型干净；也天然防止会员令牌越权访问管理端（查不到）。

### 4.2 拦截器

```java
public boolean preHandle(req, resp, handler) {
    if (!(handler instanceof HandlerMethod hm)) return true;   // 静态资源放行

    RequireLogin ann = hm.getMethodAnnotation(RequireLogin.class);
    if (ann == null) ann = hm.getBeanType().getAnnotation(RequireLogin.class);
    if (ann == null) return true;                              // 公开接口

    String token = req.getHeader("X-Token");

    if (ann.value() == LoginType.ADMIN) {
        String admin = tokenService.getAdminName(token);
        if (admin == null) { write401(resp, "管理员未登录或登录已过期"); return false; }
        LoginHelper.setLoginUser(LoginUser.admin(admin));
    } else {
        Long memberId = tokenService.getMemberId(token);
        if (memberId == null) { write401(resp, "请先登录"); return false; }
        LoginHelper.setLoginUser(LoginUser.member(memberId));
    }
    return true;
}

public void afterCompletion(...) { LoginHelper.clear(); }   // 必须清，否则线程池复用会串号
```

**两个易错点**：

1. `afterCompletion` 里不清理 `ThreadLocal`，Tomcat 线程复用会导致 A 用户拿到 B 用户身份。这是本设计里最危险的一处，代码中已实现清理。
2. 401 返回的是 **HTTP 200 + body code 401**，不是 HTTP 401。前端 axios 的 `validateStatus` 不会拦截，统一在响应拦截器里按 `code` 处理。

## 5. 核心业务实现

### 5.1 下单（`OrderServiceImpl#createOrder`）

```java
@Transactional(rollbackFor = Exception.class)
public MallOrder createOrder(Long memberId, OrderBody body) {
    // ① 入参校验：lines 非空 / 三字段非空 / 手机号格式
    // ② 逐行处理
    for (line : body.getLines()) {
        sku     = skuRepo.findById(line.skuId)  or throw "SKU 不存在"
        product = productRepo.findById(sku.productId) or throw "商品不存在"
        if (product.status != 1) throw "商品「x」已下架"
        if (line.qty <= 0) throw "购买数量必须大于 0"
        if (!productService.lockStock(sku.id, line.qty)) throw "商品「x 规格」库存不足"
        // 组装 OrderItem 快照
        goodsAmount += sku.price * qty
    }
    // ③ 金额
    discount = round(goodsAmount * (1 - member.discount()), 2)
    payAmount = goodsAmount - discount
    freight = payAmount >= 99 ? 0 : 8
    payAmount += freight
    // ④ 落单：orderNo = QGJ + yyyyMMddHHmmss + 6 位序列
    //    status = WAIT_PAY, payDeadline = now + 15min
    // ⑤ 保存 items（orderId 回填）
}
```

**原子性来源**：`lockStock` 是带条件的 `UPDATE`，失败即抛异常，`@Transactional` 回滚前面已锁的行。因此不需要额外的补偿逻辑。

**订单号生成**：`AtomicLong`（初值 `currentTimeMillis % 1000000`）自增后取模 6 位，与秒级时间戳组合。单机内不重复；多实例需改为雪花算法或库序列（已列入变更候选）。

### 5.2 支付（`#payOrder`）

```java
@Transactional
public MallOrder payOrder(String orderNo, Long memberId) {
    order = getOrderByNo(orderNo)
    if (!order.memberId.equals(memberId)) throw "无权操作该订单"
    if (!"WAIT_PAY".equals(order.status)) throw "订单状态不允许支付（幂等保护）"   // 幂等闸门

    for (item : items) productService.deductStock(item.skuId, item.qty)          // 锁定 → 实扣
    order.status = "PAID"; save

    points = round(order.payAmount * member.pointRate())
    memberService.addPoints(memberId, "EARN", points, "订单消费 " + orderNo)
    member.growth += order.payAmount
    order.pointsEarned = points; order.growthEarned = order.payAmount            // 供退款时按比例扣回
}
```

**幂等**：状态前置校验即闸门。重复支付第二次会因状态不是 `WAIT_PAY` 直接拒绝，不会二次扣库存或二次发积分。

**`pointsEarned` 必须落库**：退款时需要知道"当初发了多少"，无法从当前积分反推（用户可能已经花掉或签到加了分）。

### 5.3 库存四原语

```java
// ProductSkuRepository
@Modifying @Query("UPDATE ProductSku s SET s.lockedStock = s.lockedStock + :qty " +
                  "WHERE s.id = :skuId AND (s.totalStock - s.lockedStock) >= :qty")
int lockStock(skuId, qty);        // 返回 0 表示可售不足

@Modifying @Query("UPDATE ProductSku s SET s.totalStock = s.totalStock - :qty, " +
                  "s.lockedStock = s.lockedStock - :qty WHERE s.id = :skuId AND s.lockedStock >= :qty")
int deductStock(skuId, qty);

@Modifying @Query("UPDATE ProductSku s SET s.lockedStock = s.lockedStock - :qty " +
                  "WHERE s.id = :skuId AND s.lockedStock >= :qty")
int releaseStock(skuId, qty);

@Modifying @Query("UPDATE ProductSku s SET s.totalStock = s.totalStock + :qty WHERE s.id = :skuId")
int restock(skuId, qty);
```

**四条语句的共同点**：都是单条 SQL 完成的原子操作，没有"先查再写"。这是防超卖的全部秘密 —— 并发时数据库行锁保证 `WHERE` 条件求值与更新是原子的。

`deductStock` 返回 0 时抛 `库存异常，请联系客服`：正常流程不会发生（预占时已保证），出现即说明数据被人工改坏。

### 5.4 超时取消（`#cancelExpiredOrders` + `OrderTimeoutTask`）

```java
@Scheduled(fixedDelay = 30_000)
public void scan() {
    int n = orderService.cancelExpiredOrders();   // 查 WAIT_PAY 且 payDeadline < now
    if (n > 0) log.info("自动取消 {} 笔超时订单", n);
}

// 每单：releaseOrderStock(order) → status = CANCELED
```

**幂等**：`releaseStock` 带 `lockedStock >= qty` 条件，重复执行不会把锁定库存减成负数；订单状态改为 `CANCELED` 后不再被扫描条件命中。

**开关**：`app.order-timeout-scan=false` 可关闭（测试时禁用，避免干扰断言）。

### 5.5 售后（`AfterSaleServiceImpl`）

#### 申请校验链

```
类型白名单（REFUND_ONLY / RETURN_REFUND）
  → 原因非空
  → 明细存在 → 订单存在 → 归属校验（order.memberId == 当前会员）
  → 订单状态 ∈ {PAID, SHIPPED, COMPLETED}
  → 仅退款时订单必须未发货（PAID）
  → qty ∈ [1, item.qty - item.afterSaleQty]
  → refundAmount = round(item.payAmount / item.qty, 2) × qty
```

**金额按明细实付单价算**，不是按订单均价，也不是按商品原价。这样部分退款（多明细订单里退其中一件）金额才准确。

#### 审核分支

| 类型 | pass=true | pass=false |
|---|---|---|
| `REFUND_ONLY` | `finishRefund()` → `DONE` | `REJECTED` + 恢复订单状态 |
| `RETURN_REFUND` | `WAIT_RETURN`（等买家寄回） | `REJECTED` + 恢复订单状态 |

#### 退款完成（`finishRefund`）

```
1. 退货退款 → restock(skuId, qty)                    库存回补
2. ratio = refundAmount / order.payAmount
3. backPoints = round(order.pointsEarned × ratio)   按比例扣回积分
4. member.growth = max(0, growth - order.growthEarned × ratio)
5. afterSale.status = DONE
6. restoreOrderIfNeeded()：若该订单还有未退完的明细，订单状态从 AFTER_SALE 恢复到 PAID/SHIPPED
```

**成长值用 `max(0, ...)`**：多次部分退款累计扣减可能因四舍五入超过原值，用 0 兜底防止负数成长值。

### 5.6 会员（`MemberServiceImpl`）

```java
public Member login(phone, smsCode) {
    if (!DEMO_SMS_CODE.equals(smsCode)) throw "验证码错误（演示环境固定为 123456）"
    if (!StringUtils.isPhone(phone)) throw "手机号格式不正确"
    return memberRepo.findByPhone(phone).orElseGet(() -> register(phone));   // 自动注册

public int checkin(memberId) {
    // 从最近 100 条流水里找今天是否有 CHECKIN
    if (存在) throw "今日已签到";
    return addPoints(memberId, "CHECKIN", 5, "每日签到");

public int scanCode(memberId, code) {
    scanCode = repo.findByCode(code) or throw "防伪码不存在，请核对"
    if (scanCode.used) throw "该码已被使用"
    if (今日 SCAN 流水数 >= 20) throw "今日扫码已达上限（20 包）"
```

**签到判重的实现缺陷**：只扫描最近 100 条流水。若用户一天内产生 100 条以上流水（极端情况），当天的签到记录可能被挤出窗口，导致可重复签到。当前业务量下不会触发，已记入技术债。

## 6. 事务设计

| 场景 | 传播 | 回滚条件 | 说明 |
|---|---|---|---|
| 下单 | `REQUIRED` | 任何 `Exception` | 预占与建单必须同生共死 |
| 支付 | `REQUIRED` | 任何 `Exception` | 扣库存、发积分、改状态同事务 |
| 取消 / 超时取消 | `REQUIRED` | 任何 `Exception` | 释放库存与改状态同事务 |
| 售后申请 | `REQUIRED` | 任何 `Exception` | 建售后单 + 累加 `afterSaleQty` + 改订单状态 |
| 售后审核（仅退款） | `REQUIRED` | 任何 `Exception` | 退款 + 扣积分 + 改状态 |
| 库存调整 | `REQUIRED` | 任何 `Exception` | 单表更新 |

**统一用 `rollbackFor = Exception.class`**：Spring 默认只对 `RuntimeException` 回滚，显式声明避免受检异常漏回滚。

**没有使用分布式事务**：所有操作在单库单事务内，不涉及跨服务。

## 9. 已知技术债

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | `todaySales` 恒为 0 | 看板少一个真实指标 | 新增 `payment_flow` 表或订单加 `pay_time` |
| 2 | 令牌无过期、存内存 | 重启登出、不能多实例 | 换 JWT 或 Redis |
| 3 | 订单号靠 `AtomicLong` | 多实例可能重复 | 雪花算法 |
| 4 | 签到判重只看最近 100 条流水 | 极端情况可重复签到 | 单独查"今日是否已签到" |
| 5 | 库存调整留痕仅日志 | 无法审计 | 建 `stock_flow` 表 |
| 6 | 看板用 `LIMIT 1` 求 count | 数据量大时慢 | 改 `countByStatus` |
| 7 | 管理员账号硬编码 | 无法改密码、无多账号 | 建 `sys_user` 表 |
| 8 | 全量 CORS `*` | 生产不安全 | 白名单域名 |
